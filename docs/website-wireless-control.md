# Website USB / ESP32 control — current buffered implementation

Use the [competition runbook](competition-setup.md) as the operating authority.

From `frontend/`, `npm run competition` builds and starts the unified production website at **http://localhost:3002/control**. It supports both Arduino USB and ESP32 Wi-Fi. `npm run start:competition` restarts an unchanged build; `npm run dev:wireless` is the development alternative using a separate cache, not a second simultaneous controller.

Choose **Robot connection → ESP32 Wi-Fi → Connect ESP32**, or stop and switch to **Arduino USB** for Web Serial. Reconnect and Play are explicit. The Mac and ESP32 must share the tested LAN/hotspot. The website defaults to bridge address `172.20.10.3`; override `ANGKLOBOT_BRIDGE_HOST` if DHCP changes it. Credentials stay server-side in the ignored bridge config or environment.

Unlike the earlier per-note HTTP prototype, this implementation uploads a **complete buffered schedule** before ARM. The bridge must answer `SCHED,CAPS` with `SCHED,1,4096`. The website uploads ordered batches, arms, and requests a delayed RUN. Browser audio estimates the same start time. Keepalives maintain the schedule lease; late starts, upload cancellation and lost communication stop rather than replaying delayed notes.

Every uploaded note is capped at **2000ms**, including older/imported schedules. The Mega's separate protocol hard ceiling remains 5000ms; its firmware calibration/mapping were not changed by the website integration. Extra pulses and musical rests are generated by the shared scheduler. Stop/E-stop cancels the schedule and sends ESTOP; the physical cutoff remains available for network failure. The USB-only wake sweep is not supported by the ESP32 bridge.

On 2026-09-10 the operator confirmed Wi-Fi song playback works. Native tests cover bridge buffering/deadlines/lease expiry; browser-transport tests cover uploading before ARM, two-second caps, cancellation and legacy-bridge rejection. These tests do not establish the installed firmware revision or powered fail-stop behavior. See the runbook's outstanding pin-42 discrepancy.

The competition server binds to loopback. The wireless route also rejects disabled, external-origin, forwarded and unsupported requests. Do not publicly expose the ESP32 endpoint or share its token.
